# 全流程优化策略

## 一、幻觉抑制方案

### 1.1 Prompt 层面优化

**核心策略：严格约束 + 引用标注 + 诚实告知**

```
核心原则：
1. 严格基于文档：所有回答必须完全基于提供的参考文档内容
2. 诚实告知：如果文档中没有答案，明确说不知道
3. 引用标注：每个关键信息都必须标注来源
4. 准确优先：宁可简短准确，也不要为了全面而牺牲准确
```

**实现方式：**
- 系统 Prompt 中明确角色设定和行为约束
- 要求模型在回答中标注 [来源N] 引用标记
- 明确禁止编造、推测、引入外部知识
- 设计回答结构：直接回答 → 详细说明 → 引用来源

### 1.2 检索层面优化

**核心策略：提升召回率和准确率，确保相关文档被检索到**

本项目的四条检索优化手段：

| 优化手段 | 说明 | 状态 |
|---------|------|------|
| 混合检索 | 向量检索 + BM25 关键词检索双通道，分数归一化后加权融合 | 已实现（权重 0.6 / 0.4） |
| Rerank 精排 | 交叉编码器对候选重新打分 | 代码链路完整，**默认关闭**（`ENABLE_RERANK=false`，`FlagEmbedding` 未进默认依赖） |
| 问题改写 | 结合历史上下文把指代补全成完整问句 | 已实现（`QUERY_REWRITE_PROMPT`） |
| 自适应分块 | 按文件类型调整块大小与重叠 | 已实现（`AdaptiveChunker`） |

> **为什么这里不写"召回率 +20%、准确率 +15%"这类数字**：
> 这些百分比需要"单路 vs 双路""开 Rerank vs 关 Rerank"的对照实验才能得出，
> 本项目**没有做过这类对照**，写上去就是无源数据。
>
> 本项目**真实可复现**的只有一组数据 —— 分块参数的 A/B 评测：

评测集：仓库内 `eval_data/`，20 篇文档 + 40 道人工标注问题（正确文件 + 答案关键词双重判定）。

| 配置 | 块数 | 平均块长 | Recall@1 | Recall@3 | MRR | 平均 Top1 分数 |
|------|------|---------|----------|----------|-----|---------------|
| chunk_size=256 / overlap=32 | 40 | 169.0 字符 | 97.5% | 100.0% | 0.988 | 17.23 |
| chunk_size=512 / overlap=64 | 20 | 340.0 字符 | 100.0% | 100.0% | 1.000 | 13.74 |

复现命令：`python scripts/ab_chunk_size.py`

评测口径（必须一并说明，否则会被误读）：
- 语料为 20 篇 RAG/工程主题短文，512 分块下每篇约 1 块、256 分块下约 2 块，两者的差异主要来自"是否把答案关键词切到另一个块"；
- 评测集为 40 道人工标注问题，判定标准是"正确文件的块进入 top-k 且块内含答案关键词"；
- **只跑了 BM25 单通道**，未跑向量检索与混合检索；
- Recall@3 两种参数均为 100%，说明在这个语料规模下分块影响的是**排序精度**而非**能否召回**；
- 256 下唯一未首位命中的问题是「流式输出优化的到底是什么？」（正确答案被切到第二块，排名掉到第 2），512 下恢复第 1 —— 这正是"块切断了语义"的典型样本。

结论：这组实验的价值在于**把分块参数从"凭经验"变成"可复现的选择"，并且能指出失败样本的成因**；它不构成"检索效果大幅提升"的证据。真实语料需用同一脚本（替换 `eval_data/`）重跑后再定参。

### 1.3 答案验证机制

**核心策略：回答生成后进行幻觉检测**

- 引用一致性检查：验证回答中的事实是否都能在引用文档中找到
- 关键信息比对：数字、日期、名称等精确信息与原文比对
- 置信度评估：对回答的可靠性进行评分

**当前实现状态（不要说得比代码更满）：**

| 手段 | 实现位置 | 默认 | 说明 |
|------|---------|------|------|
| 检索为空 / 低分拒答 | `ChatManager._should_refuse` + `_build_refusal_answer` | 开启（阈值 `ANSWER_MIN_SCORE=0.0`） | 拒答时**不调用大模型**，直接返回"未找到"文案 + 三条建议；判定依据写入 `metadata.refused / refuse_reason / top1_score` |
| 生成后引用校验 | `ChatManager._verify_answer` + `HALLUCINATION_CHECK_PROMPT` | 关闭（`ENABLE_CITATION_CHECK=false`） | 让模型自查答案是否被材料支持，返回 JSON 解析后写入 `metadata.citation_check`；解析失败或模型异常只降级、不打断回答 |
| 逐句引用溯源 | `_extract_sources` | 开启 | 从回答里解析 `[来源N]` 标记映射到文件/页码；**回答中没有标记时会兜底展示前 5 个检索片段**，这属于"展示相关片段"，不是严格逐句溯源 |

**已知边界**：引用校验依赖模型自评，属于"弱验证"——它能提示风险，不能保证正确；
需要强保证时必须外接人工标注或独立 NLI 模型，本项目没有做这一步。

## 二、检索准确率优化

### 2.1 混合检索架构

```
用户问题
    │
    ├─→ 向量检索（语义匹配）
    │   └─ 嵌入模型 → 向量数据库 → 相似度计算
    │
    ├─→ BM25 检索（关键词匹配）
    │   └─ 倒排索引 → 词频统计 → BM25 评分
    │
    └─→ 结果融合
        ├─ 去重合并
        ├─ 加权融合（向量权重 0.6 + BM25 权重 0.4）
        └─ 分数归一化
            │
            ↓
        Rerank 精排
            │
            ↓
        最终结果
```

### 2.2 向量检索优化

**嵌入模型选择：**
- 当前使用：经 MaaS 网关的 OpenAI 兼容嵌入接口（`qwen3.7-text-embedding-flash`，1024 维）
- 可切换：`EmbeddingManager` 支持 `provider=local`，走 HuggingFace 中文模型（默认 `BAAI/bge-small-zh-v1.5`）
- 注意：**换嵌入模型必须全量重建索引**，不同模型的向量空间不兼容，即使维度相同

**检索参数调优：**
- Top K：默认 10（平衡召回率和噪声）
- Rerank 保留数：默认 5（仅在启用重排时生效；关闭时进 Prompt 的是 Top K=10 个块）
- 相似度阈值：**当前未实现**（没有分数阈值拒答机制，属待补项）
- 元数据过滤：按文件名等条件过滤（`retrieve(..., filter=...)`）

### 2.3 BM25 检索优化

**中文分词：**
- jieba 分词：准确的中文分词
- 停用词过滤：去除无意义的停用词
- 同义词扩展：提升召回率

**参数调优：**
- k1 = 1.5：词频饱和度参数
- b = 0.75：文档长度归一化参数

### 2.4 Rerank 重排优化

**重排模型选择：**
- BAAI/bge-reranker-large：中文效果优秀，开源可本地部署
- Cohere Rerank：商业 API，效果极佳

**重排策略：**
- 初始检索 top_k = 10
- 重排后返回 top_n = 5
- 交叉编码器计算精确相关性

## 三、文档处理优化

### 3.1 智能分块策略

| 文档类型 | 分块策略 | 块大小 | 重叠 |
|---------|---------|--------|------|
| PDF | 递归字符分块 | 512 字符 | 64 字符 |
| Word | 递归字符分块 | 512 字符 | 64 字符 |
| PPT | 按页分块 | 512 字符 | 32 字符 |
| Markdown | 标题分块 | 自适应 | 自适应 |
| Excel/CSV | 按行分块 | 1024 字符 | 0 |
| 纯文本 | 递归字符分块 | 512 字符 | 64 字符 |

**分块原则：**
1. 优先在语义边界分割（段落、句子）
2. 相邻块保留重叠，避免上下文断裂
3. 保留完整元数据，便于溯源
4. 按文档类型调整分块参数

### 3.2 增量更新机制

**基于文件哈希的增量检测：**
```
文件扫描 → 计算 MD5 哈希 → 与元数据比对
    ├─ 新增文件 → 解析 → 分块 → 入库
    ├─ 修改文件 → 删除旧版本 → 重新解析入库
    ├─ 未变文件 → 跳过
    └─ 删除文件 → 从知识库中删除
```

**优势：**
- 大幅提升更新效率（只处理变化的文件）
- 节省计算资源
- 支持批量增量更新

## 四、多轮对话优化

### 4.1 问题改写

**核心思路：** 结合对话历史，将用户当前问题改写为独立完整的问题

**示例：**
```
用户1：什么是 RAG？
助手1：RAG 是检索增强生成...

用户2：它有什么优势？
        ↓ 改写
用户2'：检索增强生成（RAG）有什么优势？
```

**效果：**
- 提升多轮对话的检索准确率
- 解决指代消解问题
- 保持对话连贯性

### 4.2 对话历史管理

**滑动窗口机制：**
- 保留最近 N 轮对话（默认 10 轮）
- 超出窗口的对话被截断
- 控制 token 消耗

**Token 控制：**
- 实时计算历史 token 数
- 超过阈值时从前往后删除
- 保证上下文在模型限制内

## 五、性能优化

### 5.1 批量处理

- 文档批量解析和分块
- 批量向量化（减少 API 调用次数）
- 批量检索和重排

### 5.2 缓存机制

- 嵌入结果缓存：相同文本直接返回缓存
- 检索结果缓存：相同查询直接返回缓存
- LLM 响应缓存：完全相同的问题直接返回

### 5.3 异步处理

- 文档上传异步处理
- 流式输出提升体验
- 非阻塞 UI 交互

## 六、准确率评估指标（设计目标，尚未验证）

> ⚠️ 下表是**设计目标**，不是已达成结果。
> 当前项目没有生成侧黄金集，只有检索侧的 `scripts/ab_chunk_size.py`
> 在 10 个问题上跑出的 Recall@1 / MRR（见 1.2 节）。
> 没有测量过程的目标不应对外表述为"系统指标"。

| 指标 | 说明 | 目标值 |
|------|------|--------|
| 召回率 (Recall) | 相关文档被检索到的比例 | ≥ 90% |
| 精确率 (Precision) | 检索结果中相关的比例 | ≥ 80% |
| Top-5 准确率 | 前 5 个结果包含正确答案的比例 | ≥ 95% |
| 回答准确率 | 回答正确的比例 | ≥ 90% |
| 幻觉率 | 回答中包含编造内容的比例 | ≤ 5% |
| 引用准确率 | 引用来源正确的比例 | ≥ 95% |

## 七、常见问题与解决方案

### 7.1 检索不准

**问题表现：** 检索到的文档与问题不相关

**解决方案：**
1. 调整分块大小（尝试 256/512/1024）
2. 增加 top_k 值
3. 启用 Rerank 重排
4. 优化问题改写
5. 检查文档质量

### 7.2 回答幻觉

**问题表现：** 回答中包含文档中没有的内容

**解决方案：**
1. 加强 Prompt 约束
2. 增加引用标注要求
3. 降低 temperature（0.1-0.3）
4. 增加检索结果数量
5. 启用答案验证

### 7.3 上下文丢失

**问题表现：** 分块导致上下文不完整

**解决方案：**
1. 增加分块重叠比例
2. 增大分块大小
3. 使用父子分块策略
4. 增加上下文窗口

### 7.4 多轮对话理解差

**问题表现：** 无法理解上下文指代

**解决方案：**
1. 启用问题改写
2. 增加历史轮数
3. 优化对话 Prompt
4. 使用更强大的模型
